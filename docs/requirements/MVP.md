## Goal and intended user

A person monitoring one residential solar installation can answer: "How much solar power is being generated, how much power is the home consuming, what is the battery level, and how have those readings changed over the last day?"

The installation consists of solar panels, a battery, and an inverter. The MVP demonstrates a complete path from persisted simulated measurements through PostgreSQL and the ASP.NET Core API to React. It does not model every physical component separately.

## Owner-confirmed scope

- One residential installation, using clearly identified simulated data.
- Current solar generation power in watts (W).
- Current household consumption power in watts (W).
- Battery state of charge in percent (%).
- The date and time of the latest measurement.
- Charts covering the most recent 24 hours.
- Correct distinctions and labels for instantaneous power (W) and accumulated energy (Wh/kWh).
- A first working React/API/PostgreSQL delivery early in development, rather than completing all backend layers before building the frontend.

## Approved operating defaults

The owner approved these operating defaults alongside the MVP requirements. In particular, the approval confirms one reading per minute, staleness after five minutes, manual refresh, UTC storage with local-time display, and deferral of accumulated-energy calculations. The scope and acceptance criteria remain unchanged.

| Topic | Approved default |
| --- | --- |
| Installation | One fixed development installation identified as `residential-demo`; no registration or selection screen |
| Simulator cadence | One complete reading per minute; reproducible values for a fixed seed and time range |
| Demo history | A development command can seed a full 24-hour period ending at a chosen UTC reference time; a continuous mode can subsequently submit new readings |
| Freshness | A reading is stale when it is more than five minutes old, using the server's UTC reference time |
| History window | Include readings in `[T - 24 hours, T]`, with `T` captured once per request by the server in UTC |
| Browser time | Display timestamps in the browser's local time zone and identify that zone; retain UTC instants in transport and storage |
| Refresh | Fetch when the page opens and provide an explicit refresh action; automatic polling and SignalR are later enhancements |
| Chart gaps | Preserve missing samples; break the line when adjacent readings are more than five minutes apart |

## Measurement glossary and logical contract

Each reading is a snapshot of the installation at one instant, with all three metrics measured together. The following logical fields define meaning and units; the first slice's concrete HTTP route and database layout are documented in [latest-reading.md](../architecture/latest-reading.md).

| Field | Meaning | Validation |
| --- | --- | --- |
| `installationId` | Fixed identity of the demo installation | Must identify the configured single installation |
| `measuredAt` | When the simulated measurement was taken, not when the UI loaded | Required timestamp with an explicit UTC/offset designation; normalize to UTC; reject instants later than server time |
| `solarPowerW` | Instantaneous power generated by the panels | Required finite number, at least 0; zero is valid, including nighttime |
| `consumptionPowerW` | Instantaneous power consumed by the household | Required finite number, at least 0; not net grid import/export |
| `batteryStateOfChargePercent` | Battery state of charge, not battery power or stored energy | Required finite number from 0 through 100, inclusive |

API responses supply an `asOf` UTC timestamp as reference-time metadata for freshness and history boundaries. It is distinct from `measuredAt` and must never be presented as the last measurement time.

Power and energy are different quantities:

- **W** measures power at an instant; the power charts use W on their value axis.
- **Wh** measures energy accumulated over an interval; 1 kWh equals 1,000 Wh.
- Constant generation of 500 W for two hours yields 1,000 Wh, or 1 kWh. Adding the numeric power samples alone does not calculate energy.
- Battery charge percentage cannot be converted to stored Wh without battery capacity and other assumptions.

Accumulated-energy totals and energy integration across incomplete samples are outside this MVP. The MVP displays power and charge history with correct units; it does not label power values or their unweighted sum as energy.

## User scenarios and acceptance criteria

The criteria below describe the completed MVP. The first implementation delivery intentionally covers only the subset identified in the next section.

| ID | Scenario | Observable acceptance criteria |
| --- | --- | --- |
| AC-01 | Identify the demo | The page identifies one residential installation and labels its readings as simulated. There is no installation selector or sign-in flow. |
| AC-02 | Inspect the current snapshot | Given stored readings, React obtains the latest one through the API from PostgreSQL and displays generation in W, consumption in W, battery charge in %, and its measurement date/time. All displayed current values come from the same reading with the greatest `measuredAt`. |
| AC-03 | Verify persistence | Given a stored reading, restarting the API and reloading React with PostgreSQL data retained produces the same values and measurement timestamp. The server does not substitute a hardcoded fixture or an in-memory collection for the stored result. |
| AC-04 | Distinguish UI states | While a request is pending, the page indicates loading. With no readings, it displays an explicit empty state without invented zeros. On a failed request, it displays an error and a retry action. A refresh fetches current data again; failed refreshes do not present retained values as successfully refreshed. |
| AC-05 | Interpret time and freshness | UTC instants are returned with an explicit UTC designation and displayed in the browser's identified local zone. A reading exactly five minutes old is fresh; one older than five minutes is labeled stale while retaining its actual values and timestamp. Missing data has no fabricated timestamp. |
| AC-06 | Explore the last 24 hours | For server reference time `T`, the API returns stored readings inside the inclusive 24-hour window, sorted by `measuredAt` ascending. Tests with a fixed `T` cover both boundaries and points just outside them. Charts display solar and consumption power in W and battery charge in % on separate value scales, with timestamps. |
| AC-07 | Handle incomplete history | An empty window has an explicit empty state. A partial window shows only available samples, with a partial-data indication if it does not cover the expected minute cadence. Missing readings are not replaced by zeros or fabricated energy; gaps longer than five minutes break the chart line. |
| AC-08 | Validate readings | Invalid timestamps, future instants, unknown installation IDs, missing metrics, negative power, non-finite values, or charge outside 0–100 are rejected with a clear validation error (HTTP 400 for ingestion). Nothing from an invalid reading is persisted. Boundary values of 0 W, 0%, and 100% are accepted. |
| AC-09 | Handle duplicates | A second reading for the same installation and normalized measurement instant is rejected with HTTP 409, whether its values match or differ. The original row remains unchanged. Offsets denoting the same instant count as duplicates. |
| AC-10 | Handle out-of-order arrivals | A valid older reading can be stored and appear in its historical position. It does not replace a newer reading in the current snapshot. |
| AC-11 | Reproduce a demonstration | Documented local commands create the required schema, populate deterministic simulated history, and run the app. Repeating seed preparation with the same inputs produces the same logical readings without accumulating duplicates; reset/reseed is explicit and limited to the development database. |
| AC-12 | Demonstrate the complete journey | Relevant unit tests cover actual measurement rules; integration tests exercise the API with PostgreSQL; at least one Playwright test verifies the core browser journey against the running API and database. The README records setup, actual verification, and remaining limitations. |

For empty latest-reading queries, return a successful response with no current reading and an `asOf` reference time; history queries return an empty collection. Errors must remain distinguishable from empty results. Response shape details belong in the first slice's documented API contract.

## First implementation delivery: persisted latest reading

The first feature PR will connect all three main technologies with one narrow outcome:

1. Configure a local PostgreSQL database and introduce only the EF Core schema/migration needed for one installation's reading snapshots.
2. Provide a development-only way to insert a known simulated reading; a continuous simulator is not required for this delivery.
3. Expose the latest persisted reading and its reference-time metadata through the ASP.NET Core API.
4. Fetch and display it in React, including units, the measurement timestamp, simulated-data identification, and loading/empty/error states.
5. Add focused verification and local setup instructions in the same delivery.

**Completion evidence:** demonstrate AC-01 through AC-05 with a known fixture such as 1,200 W solar generation, 800 W consumption, and 65% battery charge. Verify the API against a real PostgreSQL instance and verify the browser against that API; record exact checks and results in the PR. Include relevant tests for the behavior introduced and an automated browser smoke test for the persisted-reading journey. Removing the data must produce the empty state; restarting the API must preserve the stored result.

This delivery does not require charts, 24-hour seeding, continuous ingestion, or a finished UI component system. Implement only the domain/application logic required by the slice, while preserving the existing project dependency direction. Later PRs complete the simulator/ingestion behavior, then 24-hour history and charts.

## Scope boundaries

The MVP excludes real hardware/protocol integrations, authentication, multiple users, multiple installations, per-device management, grid import/export accounting, battery charge/discharge control, physical inverter simulation, alerts, forecasts, billing, accumulated-energy totals, and production deployment.

Authentication and access requirements must be reconsidered before any public deployment. This local, unauthenticated demonstration is not a production deployment specification.

Keep one API, one PostgreSQL database, one React client, and a small development simulator. No message broker, microservices, event-sourcing framework, generic repository framework, or separate read/write infrastructure is required by these scenarios. Introduce dependencies only when an accepted slice needs them.
